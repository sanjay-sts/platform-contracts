FoundryCore · platform consolidation · 2026-08-02 · design approved, spec in review

Two Products, One Protocol

Five repos become two open-source products — a server platform and a sovereign desktop platform — bound by one published contract, with a commercial governance tier layered cleanly on top.

owner Sanjay license Apache 2.0 + DCO launch story chat anywhere · sync offline · ship in one click

01Why consolidate

Three drivers, weighted equally, shaped every decision below.

Coherent public story. Five loosely-related repos confuse visitors; two well-named products with one protocol attract users and contributors. Sustainable maintenance. One maintainer cannot keep five stacks alive; every surface below is either a product or archived. Commercial path clarity. The free/paid seam is decided now, so the open-source core never has to claw features back.

The launch pitch: “Chat with your server’s agents from any browser or phone. Sync skills and knowledge to your laptop and go fully offline. Vibe-code an app locally and ship it to your server in one click.” No open-source project tells that whole story today.

02High-level architecture

Rejected framing: “one engine, two interfaces.” Adopted framing: one platform contract, two engine implementations — the desktop is not a thin client; its air-gapped value requires a full local engine.

The federation principle survives intact: every agent remains a standalone container with its own A2A endpoint, and state flows by message-passing — the contracts repo simply makes the messages canonical.

04Platform objects & knowledge

The registry manages seven object types, synced by one mechanism.

  • agents
  • MCP servers
  • skills
  • prompts
  • apps
  • policies
  • knowledge bundles

Knowledge bundles adopt Google’s Open Knowledge Format (OKF) — directories of Markdown with YAML frontmatter, distributed as git repos or archives. Bundles carry documents only, never embeddings: each engine builds its own local index (SurrealDB server-side, pgvector on the desktop), the same way a database builds its own btrees. OKF’s trust frontmatter (generated, verified, sources, status, stale_after) is adopted as-is.

The spec is two months old with no established server ecosystem — native OKF support is a launch differentiator, and it is structurally a sibling of the agentskills.io pattern SkillHub already serves.

05Desktop ↔ server integration

Four flows on the roadmap. V1 builds two; the other two are deliberately deferred, not forgotten.

Desktop sign-in follows the Claude Code / Amazon Q pattern: the app opens the system browser for one OAuth 2.1 PKCE dance against agentprint; agentprint brokers every IdP server-side. The desktop never contains per-IdP code, and air-gapped machines use local accounts with no IdP at all. The PKCE machinery already exists in the desk agent’s Phase 7 MCP auth pyramid.

06Vibe-coding & local models

POCForge graduates into agentprint at launch — the OpenCode subprocess pipeline, chat-to-code UI, live preview, and three deploy modes. It lands behind a thin coding-backend adapter (start session · send prompt · stream events · get changed files) with OpenCode as the only launch implementation. The seam is what lets users select their own AI coding tool later — Claude Code CLI, Aider, or anything else — one adapter file per backend, and an attractive contributor entry point.

Desktop vibe-coding is deferred. The partial Go implementation is parked; the desktop reuses the adapter contract in a later phase, after agentprint has productized it once.

Ollama is a first-class optional provider in both engines. On the desktop it makes the air-gapped story literally true — offline chat and offline embeddings for knowledge search. In agentprint it slots in via the adapter and the AI-assisted creation flows for agents, MCP servers, skills, and prompts.

08Open source vs commercial

Individuals get real security free; organizations pay for governance. Commercial code lives in a separate private repo from day one — the OSS repos never contain paid code.

OPEN SOURCE · APACHE 2.0

  • Local users + API keys, single OIDC provider
  • Cedar RBAC with tool-level restriction, 3 principals
  • Workload identity + mandatory tagging
  • Single-admin intake (register → validate → approve)
  • Desktop local-only ACL
  • TLS everywhere + workload tokens
  • Vibe-coding, registry, chat, OKF — the whole product story

COMMERCIAL · CLOSED MODULES

  • Multi-IdP dispatch (Entra + Cognito + …)
  • Cedar ABAC on runtime attributes
  • RFC 8693 delegation chains, OBO token exchange
  • Budget & rate-limit enforcement
  • Multi-stage approval workflows, audit trails
  • Policy/identity push to desktops (flow ④)
  • mTLS multi-host deployments

Contributions under DCO, not a CLA. And the real moat is neither: register the trademark on the eventual brand — anyone can fork Apache code; nobody can fork the name.

09Sequencing

Ordered for one maintainer: contracts first, auth before public API surface grows, the demo feature on top, integration last — because the integration is the launch story.

  1. Foundations.

    Contracts repo v0.1 (tag vocabulary, registry sync, deploy push, agent card, workload identity). GitHub org. Branding decision gates launch — not the build.

  2. agentprint: unified registry + chat.

    Absorb SkillHub; add prompts and OKF knowledge bundles; ship the chat surface in the web UI.

  3. agentprint: identity core.

    Cedar RBAC, three principals, workload identity issuance, tagging, single-admin intake — before the API surface is public, so auth is never a retrofit.

  4. agentprint: vibe-coding graduates.

    Coding-backend adapter + OpenCode implementation; POCForge pipeline and deploy modes fold in.

  5. Desktop integration.

    Flows ① + ②, PKCE login, Ollama + local OKF embedding index, rename under the new brand.

  6. Public launch.

    Announcement, docs polish, the integrated demo. Commercial modules begin only after launch traction — a paid tier before free-tier users is built on air.
